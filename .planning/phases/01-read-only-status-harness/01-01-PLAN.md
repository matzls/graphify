## Decision Coverage Markers

- D-01: Phase 1 keeps the harness private/internal and does not add a public Graphify CLI command.
- D-02: `graphify/status_harness.py` and `graphify/status_profiles.py` provide structured internals that can later be promoted if stable.
- D-03: Read-only probes and before/after target status checks prove repeatable Second Brain runs without mutation.
- D-04: The harness emits both JSON and Markdown.
- D-05: JSON is the authoritative payload and Markdown is rendered from it.
- D-06: Markdown is constrained to status, diagnosis, evidence, and next action.
- D-07: Report writing targets the controlled phase reports directory, not the consumer repo.
- D-08: Diagnosis is diagnostic-by-default.
- D-09: Strict acceptance mode stays deferred and is not implemented in Phase 1.
- D-10: Severity values are `pass`, `warn`, `fail`, and `info`.
- D-11: Local fork source mismatch is a `fail`.
- D-12: Installed Codex skill drift is `warn` or `fail` depending on load-bearing guidance impact.
- D-13: Target graph built commit differing from target HEAD is `warn` by default.
- D-14: Missing expected hidden-path coverage for `.claude/scripts/**/*.py` is `fail` for the Second Brain profile.
- D-15: Missing semantic cache is `warn` before approved refresh expectations exist.
- D-16: Ollama unavailable is `warn` for readiness mode and `fail` for generation/stress mode.
- D-17: Small generation pass plus larger stress timeout is `warn` by default.
- D-18: Phase 1 supports Second Brain-specific expectations.
- D-19: Second Brain expectations are expressed through `TargetProfile` data rather than scattered hardcoding.
- D-20: The Second Brain profile covers activation, include/ignore behavior, graph freshness, cache status, and smoke-query concepts.
- D-21: Local Ollama generation checks are included because paid API cost is not the constraint.
- D-22: Ollama readiness is separate from generation/stress checks.
- D-23: Readiness reports backend, local availability, models, zero priced backend cost, and runtime risk.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Harness -> target repo filesystem | Target repo files and graph artifacts are untrusted input and must only be read. |
| Harness -> Git subprocess | Git output can fail, be absent, or include unexpected text; classify as structured evidence. |
| Harness -> installed global skill | `/Users/mase/.codex/skills/graphify/SKILL.md` is outside the repo and must be compared, not overwritten. |
| Harness -> local Ollama endpoint | Local service probing may reveal model names and can become a remote data boundary if endpoint is non-loopback. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | target repo probes | mitigate | Use read-only file reads and `git -C` status/rev-parse commands only; tests assert target status remains unchanged. |
| T-01-02 | Information Disclosure | report payload | mitigate | Store only statuses, hashes, counts, paths, and short diagnostic snippets; do not copy target file contents or secrets into reports. |
| T-01-03 | Spoofing | active CLI source | mitigate | Verify active install source against `/Users/mase/Codebase/Personal-Projects/graphify` and classify mismatch as fail per D-11. |
| T-01-04 | Denial of Service | Ollama readiness probe | mitigate | Bound subprocess/HTTP timeouts and keep live generation out of default readiness checks. |
| T-01-05 | Elevation of Privilege | target hook/code execution | mitigate | Do not execute target hooks, imports, scripts, or Graphify refresh commands; only inspect hook marker status. |
| T-01-SC | Tampering | package installs | mitigate | Production harness code uses stdlib and existing Graphify modules; the only package metadata change is dev/test `pytest` from the RESEARCH.md Package Legitimacy Audit, installed through `uv sync --group dev`. |
</threat_model>
